## How to read this plan

- **Plane coordinates**: overworld tile (x, y) of `world_X_Y[_Z]` is plane (24X+x, 24Y+y) on layer Z. Overworld plane extent: x -240..479, y 0..2159.
- **Group-local layout**: each member map gets a local origin by walking tile links from the layout root (N/S/E/W/diagonal neighbours offset by the neighbour's or the map's own width/height exactly like the server's `get_map_from_coord()`, up/down = local layer +1/-1; a root with filename coordinates starts at (X*w, Y*h, Z)). The layout is copied unchanged: plane tile = local origin + (x, y) + (x_offset, y_offset); plane layer = local layer + layer_offset.
- **Exit resolution** mirrors the server: `slaying` path relative to the map directory or absolute; `hp/sp` target (-1/-1 = the map's enter_x/enter_y); `last_heal` 1..10 = tiled exit through that tile link (with the `xrays` direction offset); coordinates outside the target map walk its tile links.
- **Layer choice**: the main connection fixes the ideal layer: one layer below its source for down-exits (stairs/ladder down, holes, wells with a bucket), one layer above for up-exits. Neutral exits (exit, invis_exit, portals) take the group's orientation, which comes from the exit semantics of its connections to the overworld or upstream groups, then name keywords, then the default (dungeon-like, below). Every directional exit to an already placed thing is also a hard bound (a group entered by stairs down must lie below the stairs).
- **Main connection**: among all exits between the group and already placed things, the candidate alignment that turns the most exit sites into stairs wins. Ties go to overworld entrances, then to stairs-like exits, then lexicographic order.
- **Collisions**: a group may not overlap or touch (margin 1 tile) any overworld map on the same layer or any already placed group. If the ideal spot collides, the next 3 deeper (or higher) layers are tried, then horizontal shifts up to 96 tiles. Primary footprint = full map rectangles; the alternative footprint counts only tiles holding at least one object.
- **becomes**: `stairs` = after placement the two ends are exactly one layer apart and <= 1 tile apart horizontally (can be a plain stair/ladder/hole); `aligned>1 layer` = horizontally aligned but more than one layer apart (a shaft would be needed); `portal` = still a teleport.

## Reproducing

```sh
cd /home/zoey/dev/atrinik-placement-plan
python3 -I scripts/build_plan.py --content /home/zoey/dev/atrinik/content --out .
```

The run is deterministic (sorted inputs, lexicographic tie-breaks) and read-only against the content checkout; it rewrites `placement-plan.json`, `REPORT.md` and the PNGs. `content_git_head` and `content_maps_digest_sha256` in the JSON identify the input. Scripts: `mapdata.py` (parser, tile links), `analysis.py` (components, layout, exit resolution), `build_plan.py` (classification, placement, JSON), `report.py`, `render.py`. Tunables (`MARGIN`, `MAX_EXTRA_LAYERS`, `MAX_SHIFT`, `STAIR_TOLERANCE`) and the few hand-written classification inputs (system maps, owner directives, the Rockforge mines alignment hint) are constants at the top of `build_plan.py`.
