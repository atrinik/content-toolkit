3. **Footprint = occupied tiles plus a view gap.** A map occupies only tiles holding at least one object; every other legacy tile is void. On each layer a placed group keeps more than 16 tiles (Chebyshev) between its occupied tiles and those of every area it shares no exit with (other placed groups, overworld maps), so at least 16 void tiles lie between them and neither can be sent a tile of the other. Areas that share an exit need no gap; they only keep 1 void tile so they do not merge into one walkable area. The radius comes from the classic sources ([View radius](#view-radius)).
4. **Long staircases instead of shafts.** Every exit whose ends are 2 or more layers apart and at most 1 tile apart horizontally is replaced by a stairwell: one stair tile on every intermediate layer at the aligned x/y, built from the stair archetype the stairwell's own exits use. Each intermediate tile must be void in every existing map; where the column is not free the chain may bend up to 2 tiles (one tile per layer), and where no chain exists the exit stays a portal and is reported. 14 stairwells were built; see [Stairwells](#stairwells). The whole stairwell is one exit; see [Stairwell follow-up](#stairwell-follow-up-engine-and-format).

## View radius

Read-only sources: `atrinik/classic@b651c55fd0fe`, `atrinik/client@29cb5f66bc06`, `atrinik/server@7f80ae5f5792`.

- Classic server: `MAP_CLIENT_X 32` / `MAP_CLIENT_Y 32`, the largest map view a client may request (`server/src/include/config.h:60-61`). The setup handler accepts any requested size up to that (`server/src/socket/request.c:154-161`), and `mapx_2 = mapx / 2` (`server/src/socket/init.c:77`). The map update sends x from `pl->x - mapx_2` to `pl->x + (mapx + 1) / 2 - 1` and likewise for y (`server/src/socket/request.c:1305-1311`): **16 tiles** west and north, 15 east and south at size 32.
- Classic client: the user-visible look size is at most `MAP_LOOK_SIZE_MAX 17`, and the client adds `MAP_RENDER_OVERSCAN 2` tiles on each edge, so the size on the wire is at most 21 (`client/src/include/map.h:68-83`). The client refuses anything larger from the server (`client/src/client/commands.c:139-140`). That is **10 tiles** each way.
- Replacement stack: neither `atrinik/client@29cb5f66bc06` nor `atrinik/server@7f80ae5f5792` defines a view radius yet.
- **The plan uses 16 tiles**, the server's bound, so no client the server accepts can see from one area into an unrelated one. Comparison run with the shipped client's 10 tiles (`view_radius_sensitivity` in the JSON): 65 stairs, 32 stairwell, 35 portal; 12 stairwells; groups that would sit elsewhere: `mine_unique_a`, `dark_cave`.
- Other layers: classic also streams the linked levels from 6 below to 6 above (`MAP2_MAX_DEPTH 6`, `libatrinik/socket.h:87-89`), but levels hidden from the camera are pruned before they are sent (`server/src/server/los.c:737`). The gap rule therefore applies per layer, as decided.

## How to read this plan

- **Plane coordinates**: overworld tile (x, y) of `world_X_Y[_Z]` is plane (24X+x, 24Y+y) on layer Z. Overworld plane extent: x -240..479, y 0..2159.
- **Group-local layout**: each member map gets a local origin by walking tile links from the layout root (N/S/E/W/diagonal neighbours offset by the neighbour's or the map's own width/height exactly like the server's `get_map_from_coord()`, up/down = local layer +1/-1; a root with filename coordinates starts at (X*w, Y*h, Z)). The layout is copied unchanged: plane tile = local origin + (x, y) + (x_offset, y_offset); plane layer = local layer + layer_offset.
- **Exit resolution** mirrors the server: `slaying` path relative to the map directory or absolute; `hp/sp` target (-1/-1 = the map's enter_x/enter_y); `last_heal` 1..10 = tiled exit through that tile link (with the `xrays` direction offset); coordinates outside the target map walk its tile links.
- **Layer choice**: the main connection fixes the ideal layer: one layer below its source for down-exits (stairs/ladder down, holes, wells with a bucket), one layer above for up-exits. Neutral exits (exit, invis_exit, portals) take the group's orientation, which comes from the exit semantics of its connections to the overworld or upstream groups, then name keywords, then the default (dungeon-like, below). Every directional exit to an already placed thing is also a hard bound.
- **Main connection**: among all exits between the group and already placed things, the candidate alignment that turns the most exit sites into stairs wins. Ties go to overworld entrances, then to stairs-like exits, then lexicographic order.
- **Search**: if the ideal spot breaks the gap rule, the next 6 deeper (or higher) layers are tried at the same x/y, keeping the main connection aligned so it becomes a stairwell; a spot whose footprint fits but whose stairwell is blocked is taken next (the exit is reported); only then are horizontal shifts up to 96 tiles tried. Groups are placed in reach order, then by id.
- **becomes**: `stairs` = the two ends are exactly one layer and at most 1 tile apart; `stairwell` = 2 or more layers apart and aligned, replaced by a stairwell (id in the exit record); `portal` = still a teleport, with `portal_reason` in the JSON.

## Stairwell follow-up (engine and format)

Decided semantics: a stairwell is ONE exit for use and pathfinding, in classic and in other games. One use moves the player from one end to the other; pathfinding sees one edge; editors and players see a long staircase through the layers. Not implemented here; needed before the migration can emit stairwells:

- **Classic server** (`atrinik/classic@b651c55fd0fe`):
  - Tiled stairs move exactly one linked level: `last_heal` 9/10 resolve through one `tile_path` (`server/src/types/exit.c:300-320`), and landing picks a floor by sub-layer direction (`server/src/server/object.c:4703`). A stairwell end needs an explicit destination at the other end (layer included), not a tiled link.
  - The intermediate stair objects must not be exits (no `P_IS_EXIT`) and must not be walkable or applicable, or each would be a separate edge or a shortcut. They are decorations that belong to one stairwell record.
  - Pathfinding already treats an exit as one edge to `exit_get_destination()` (`server/src/server/pathfinder.c:1034-1078`, `server/src/types/exit.c:377`); a stairwell must resolve to its far end there, never to an intermediate layer.
  - The plane loader must create the stairwell from the plan's record and validate it (continuity, void intermediate tiles, both ends are exits that target each other's end).
- **Classic client** (`atrinik/classic@b651c55fd0fe`):
  - Linked levels are projected 46 px apart (`client/src/gui/widgets/map.c:1307`, applied at `:4712-4713`) and up to 6 levels each way are streamed (`libatrinik/socket.h:87-89`); every stairwell here spans at most 4, so its intermediate tiles can be drawn as one staircase.
  - The exit cue (`MAP2_FLAG2_EXIT`, `server/src/socket/request.c:1831`; `map_render_command_draw_exit()`, `client/src/gui/widgets/map.c:7311`) should mark the stairwell's ends as one exit, not each intermediate tile; upper levels cut away near the player must not hide the whole staircase.
- **Tilewright world format** (`seraphinastudios/tilewright-world@6c4e48c14b28`):
  - Today an exit is an object with a `portal` to `(plane, layer, at)` (`docs/spec/FORMAT.md:184`, example at `:155`; packed as one portal record, `docs/spec/PACK.md:75-76`). There is no way to say that objects on several layers form one exit.
  - Needed: a stairwell record per plane (id, ordered tiles `(layer, x, y, proto)` from top to bottom, the two end objects), validation rules (consecutive tiles one layer and at most one tile apart, the ends are portals that target each other's end, the intermediate objects are not portals), a pack table for it, and editor support to show and edit the stairwell as one object.

## Layer-height evidence

Read-only source: `atrinik/classic@b651c55fd0fe`.

- Floor z is a screen-pixel height. The server sends an object's `z` as its height (`server/src/socket/request.c:1718`, `:1965`); the client reads it (`client/src/client/commands.c:1335`) and draws the tile that many pixels higher (`client/src/gui/widgets/map.c:8499`). Negative floor heights draw as 0 (`get_top_floor_height()`, `client/src/gui/widgets/map.c:3386-3391`).
- One linked level is drawn **46 px** higher (`MAP_LEVEL_PIXEL_HEIGHT`, `client/src/gui/widgets/map.c:1307`, applied at `:4712`), on top of the floor height under it (`map_space_support_height()`, `server/src/socket/request.c:1012-1022`; `client/src/gui/widgets/map.c:4713`).
- Double wall rendering: `draw_double` objects (`server/src/socket/request.c:1742`) are drawn twice, the second copy **22 px** higher (`client/src/gui/widgets/map.c:4309`, `:7142`, `:7320`). Sprites are bottom-aligned on the 23 px tile (`MAP_TILE_POS_YOFF 23`, `client/src/include/map.h:46`; `client/src/gui/widgets/map.c:4174`). The double-drawn 48x47 wall sprites rise 47 - 23 = 24 px, and doubled 24 + 22 = 46 px: exactly one level. Most double-drawn walls are 48x38 (15 + 22 = 37 px).
- `HEIGHT_MAX_RENDER 50` (`client/src/include/map.h:319`): tiles more than 50 px above or below the player are hidden in fog of war and on height-difference maps.
- So **z 50 is about one layer**; the client's exact figure is 46 px. 606 floor tiles have 46 <= |z| < 50 and would also move under a 46 px rule; none have z <= -50.

## Layer-height relayering proposal (not applied)

Rule: tile floor z = 50 * q + rest with q = trunc(z / 50); a tile with q != 0 moves q layers and keeps rest as its tile height; 8-connected tiles with the same (layer, q) form one region. ## Reproducing

```sh
cd migration/placement-plan
python3 -I scripts/build_plan.py --content /home/zoey/dev/atrinik/content --out .
python3 -I scripts/verify_plan.py placement-plan.json
```

The run is deterministic (sorted inputs, lexicographic tie-breaks) and read-only against the content checkout; rerunning with the same arguments on the same content rewrites `placement-plan.json`, `REPORT.md` and the PNGs byte-for-byte. `content_git_head` and `content_maps_digest_sha256` in the JSON identify the input. Scripts: `mapdata.py` (parser, tile links, occupied tiles, floor z), `analysis.py` (components, layout, exit resolution), `footprint.py` (gap rule, stairwell chains), `build_plan.py` (classification, placement, stairwells, JSON), `relayer.py` (layer-height proposal), `report.py`, `render.py`, and `verify_plan.py` (independent check of the JSON). Tunables (`VIEW_RADIUS`, `CONTACT_MARGIN`, `MAX_EXTRA_LAYERS`, `MAX_SHIFT`, `STAIR_TOLERANCE`, `STAIRWELL_MAX_BEND`, `LAYER_HEIGHT_Z`) and the hand-written inputs (system maps, owner decisions, the Rockforge mines alignment hint) are constants at the top of `build_plan.py`.
